01What is this project?

local-ai-server is a single HTTP endpoint that lets any OpenAI SDK client (Python, Node, LangChain, your custom app) talk to local LLMs running on a Mac Studio — with zero code changes from the client side.

OpenAI's SDK speaks one specific HTTP shape: POST /v1/chat/completions, POST /v1/embeddings, etc. Most local model runners (Ollama, MLX, Docker Model Runner) speak something close to that shape but with quirks. This project is a small FastAPI app that:

  1. Receives OpenAI-shaped requests on a single LAN endpoint.
  2. Looks up which backend should handle the request.
  3. Forwards the call, passes the response back (streaming or not).
  4. Translates errors into the OpenAI envelope so SDK clients understand them.

From the client's perspective, only two things change versus the real OpenAI: the base_url points at your Mac Studio, and the api_key is one you minted locally. Everything else — model names, streaming, tool calls, embeddings — works as it would against the cloud.

02Mental model

Before the architecture, here's a plain-language analogy that makes the pieces stick.

The coffee shop

The project is a coffee shop. Customers (your apps) walk in and place orders in a standard format — they expect to say "a latte with oat milk" and get a latte. Different baristas (model backends) work in the back: one is great at espresso, another at filter coffee, a third at smoothies. The customer never meets the barista directly.

The front counter (the FastAPI gateway) takes the order, writes it on a slip, and walks to the right barista. A menu board (config/models.yaml) tells the front counter which drink each barista can make. Three baristas are on staff: Ollama (working), MLX (training, doesn't take orders yet), and Docker Model Runner (also training).

Over four versions, the shop adds: a door with a key card (auth — v0.2.0), a diary for what happens (logging — v0.2.0), a "we're open" sign that checks each barista (/readyz — v0.2.0), an actual storefront with a lock (Caddy + TLS — v0.3.0), and finally fully trained backup baristas (real MLX + DMR adapters — v0.4.0+).

Why backends run on the host (not in containers)

Apple Metal — the GPU API the Mac uses for fast inference — cannot be accessed from inside Docker Desktop on macOS. Docker on Mac runs Linux containers in a VM with no GPU passthrough. So:

  • Ollama in a container on Mac would fall back to CPU and run dramatically slower than native.
  • MLX in a container can't run at all — it's Mac-only and built on Metal.
  • Docker Model Runner is itself a Docker Desktop feature; it lives outside normal containers.

The gateway and Caddy do run in containers (v0.3.0+) and reach the host backends via Docker's host.docker.internal hostname. This split — light infrastructure containerized, heavy compute host-native — is the load-bearing constraint that shaped the entire design.

04Components, in detail

Each box in the architecture diagram, explained in 3–4 sentences with its inputs, outputs, and which version delivers it.

Gateway · FastAPI app v0.1.0

The translator between OpenAI v1 and your local model runners.

What it does

  • Accepts OpenAI-shaped requests (chat, embeddings, models list).
  • Mounts routes; runs lifespan startup (registry load, adapter build) and shutdown (httpx client close).
  • Installs the OpenAI-compatible error envelope handlers globally.

Where it lives

  • app/main.py, app/__init__.py

Registry v0.1.0

The menu board: which model id maps to which backend, with what capabilities.

What it does

  • Loads config/models.yaml at startup into frozen Model entries.
  • O(1) lookup by gateway-side model id (e.g. ollama-llama3).
  • Validates capabilities (chat, embeddings, tools) and rejects duplicates.
  • v0.2.0 adds atomic hot-reload via watchfiles.

Where it lives

  • app/registry.py, config/models.yaml

BackendAdapter ABC v0.1.0

The routing seam. Every backend implements four async methods; the rest of the gateway never sees backend-specific details.

The contract

  • chat_completions(body, stream) — returns dict (non-stream) or async iterator (stream).
  • embeddings(body) — returns dict.
  • health() — returns {"status": "ok" | "unreachable"}; never raises.
  • close() — releases httpx client; called on shutdown.

Where it lives

  • app/adapters/base.py

OllamaAdapter v0.1.0

The only fully-wired backend in v0.1.0. Talks to a host-native Ollama process.

How it works

  • Long-lived httpx.AsyncClient built once at startup.
  • Non-stream chat: a single POST, returns parsed JSON.
  • Stream chat: client.stream("POST", ...) + aiter_raw() + try/finally to close the upstream connection cleanly on cancellation.
  • Embeddings: passthrough POST.
  • Health: GET /api/tags with non-raising error handling.

Where it lives

  • app/adapters/ollama.py

MLXAdapter (stub) v0.4.0+

Returns HTTP 501 on every method in v0.1.0 to lock the routing seam without committing to MLX implementation details.

Why a stub now

  • Validates the BackendAdapter ABC contract.
  • Lets the registry, factory, and routers be tested with multiple backend types.
  • v0.4.0+ replaces the bodies; no other code changes.

Where it lives

  • app/adapters/mlx.py

DockerModelRunnerAdapter (stub) v0.4.0+

Same stub pattern as MLX. Returns 501; real wiring uses Docker Desktop's internal hostname.

Where it lives

  • app/adapters/docker_model_runner.py

Routers v0.1.0

Four FastAPI routers that translate the request, call the adapter, and shape the response.

The set

  • health.py — GET /healthz, public, always 200.
  • models.py — GET /v1/models, lists the registry.
  • chat.py — POST /v1/chat/completions; capability + tools gate; SSE branch.
  • embeddings.py — POST /v1/embeddings; embeddings capability gate.

Error envelope v0.1.0

All errors emerge as the OpenAI-compatible JSON shape so SDK clients can parse them uniformly.

Standard shape

{"error": {
    "type": "not_supported",
    "message": "Backend 'mlx' does not support embeddings",
    "param": "model",
    "code": "backend_capability_missing"
}}

Where it lives

  • app/errors.py

Auth middleware v0.2.0

Bearer-token gate on every /v1/* route. Public paths (/healthz, /readyz, /docs) bypass.

Verification flow

  • Extract Authorization: Bearer sk-local-....
  • Look up the 12-char prefix in SQLite (O(1)).
  • Argon2id-verify the full key against the stored hash.
  • Touch last_used_at async; pass through.
  • On miss / revoked / mismatch: HTTP 401 with the OpenAI envelope.

Where it lives

  • app/auth.py, scripts/{generate,revoke}_api_key.py

structlog observability v0.2.0

Structured JSON logging replaces stdlib logging everywhere.

Per-request fields

  • key_prefix, model, backend, stream, status, latency_ms, prompt_tokens, completion_tokens.
  • Authorization header redacted globally — never appears in logs.

/readyz v0.2.0

Smarter health check: pings each adapter's health() and reports per-backend status.

Behavior

  • Public (no auth required).
  • Returns 200 if any backend is reachable; payload lists per-backend.
  • The seam already exists in v0.1.0 (BackendAdapter.health()) — v0.2.0 just composes it.

watchfiles hot-reload v0.2.0

Mutating config/models.yaml takes effect within ~1s without a process restart.

How it works

  • Async task watches the YAML file.
  • On change: re-parse + validate. If valid, atomically swap app.state.registry.
  • In-flight requests use whichever copy was active at entry.
  • Limitation: only existing backend types. Adding a new type still needs v0.4.0+ runtime adapter construction.

Caddy reverse proxy v0.3.0

TLS termination + LAN-only binding. Uses tls internal for a self-signed cert via Caddy's local CA.

Why Caddy

  • Auto-renews internal certs; minimal config.
  • Handles SSE buffering correctly with flush_interval -1.
  • Binds explicitly to ${LAN_IP}:443, never 0.0.0.0.

Containerization (Dockerfile + Compose) v0.3.0

Gateway and Caddy ship as containers; backends stay host-native.

Container topology

  • compose.yaml with two services (gateway, caddy).
  • Gateway has no published ports — only Caddy reaches it on the internal Docker network.
  • extra_hosts maps host.docker.internal for backend reach.
  • Volumes for the SQLite key store and Caddy data.

05Request lifecycles

Two diagrams: a non-streaming chat completion (the simple case) and a streaming one with SSE (the load-bearing one).

Chat completion — non-streaming (stream=false)

Chat completion — streaming (stream=true) with SSE

The streaming flow's load-bearing trick: returning the iterator (not the awaited response) from the adapter means Starlette's StreamingResponse drives the upstream connection only when it pulls chunks. A try/finally around the aiter_raw() loop guarantees the upstream connection closes on cancellation (browser disconnect, client timeout) — preventing leaks when the client gives up mid-stream.

v0.1.0 — Skeleton + Ollama path shipped 2026-06-18 PR #1

Prove the architecture end-to-end with one real backend. MLX and Docker Model Runner exist as 501 stubs to lock the routing seam.

Delivered

  • FastAPI app with lifespan startup, error handlers, and 4 routers.
  • BackendAdapter ABC with NotSupportedError exception.
  • OllamaAdapter fully wired — chat (stream + non-stream), embeddings, health.
  • MLXAdapter + DockerModelRunnerAdapter stubs raising 501.
  • Registry loader (one-shot at startup; no hot-reload yet).
  • Capability gate (CHAT-first ordering) and tools gate.
  • 61 tests, project-mode ruff clean, demo notebook.

Key concepts introduced

  • OpenAI-compatible wire format — clients work unchanged.
  • The routing seam — every backend behind one ABC.
  • SSE streaming with cancel-safety via aiter_raw + try/finally.
  • Error envelope — uniform JSON shape for all failures.
  • Capability gating — registry decides what each model can do.
After v0.1.0 you can: point any OpenAI SDK client at http://<mac>:8000/v1, list models, run chat completions (streaming or not), and get embeddings — against a host-native Ollama — with no code changes on the client side.

v0.2.0 — Auth + Observability planning

Harden the LAN-internal seam. Add API-key auth, structured logging, a smarter health probe, and live config reloads.

Delivered

  • Bearer middleware with Argon2id verify on every /v1/*.
  • SQLite key store with prefix index + revoked timestamps.
  • scripts/generate_api_key.py + revoke_api_key.py CLIs.
  • structlog JSON logging — Authorization redacted globally.
  • GET /readyz — fans out to BackendAdapter.health().
  • watchfiles hot-reload of config/models.yaml.
  • 27 carried-forward mypy --strict cleanups.

Key concepts introduced

  • Argon2id — modern memory-hard password hashing.
  • Prefix-indexed key store — O(1) lookup before the (slow) hash verify.
  • Structured logging — JSON-per-line for log aggregators.
  • Per-backend health composition — partial-degraded service awareness.
  • Atomic config swap — hot-reload without mid-request inconsistency.
After v0.2.0 you can: mint one or more API keys, give them to teammates on the LAN, monitor which backends are up via a machine-readable /readyz, parse logs as JSON, and add a new model to models.yaml without restarting the gateway.

v0.3.0 — Containers + TLS + LAN binding planned

Package the gateway and put a real reverse proxy in front. The backends stay host-native; only the gateway and Caddy ship as containers.

Delivered

  • docker/Dockerfile.gateway — slim Python image, uv-managed deps.
  • compose.yaml with two services (gateway + caddy).
  • caddy/Caddyfile with tls internal + SSE-friendly buffering.
  • Gateway reaches host backends via host.docker.internal.
  • Caddy binds to ${LAN_IP}:443 only, never 0.0.0.0.
  • CORS allowlist; macOS firewall rule documented.

Key concepts introduced

  • Internal CA via Caddy — self-signed certs without buying a domain.
  • SSE buffering — Caddy needs flush_interval -1 or streams stall.
  • host.docker.internal — the canonical Docker-on-Mac escape hatch.
  • Bind-only-to-LAN — explicit IP binding instead of any-interface.
After v0.3.0 you can: run the entire gateway with one docker compose up, browse to https://ai.local/v1 from any device on your LAN (after trusting Caddy's local cert once), and have nothing accessible from the public internet.

v0.4.0+ — Real MLX + DMR + host-side Makefile planned

Replace the 501 stubs with real implementations. Add the missing backends and a host-side process manager.

Delivered

  • MLXAdapter wired to mlx_lm.server — one process per model, one port per process.
  • DockerModelRunnerAdapter wired to Docker Desktop's model-runner.docker.internal.
  • Registry's per-model base_url becomes load-bearing for multi-MLX.
  • Makefile with start-ollama, start-mlx MODEL=... PORT=..., start-model-runner, stop-all.
  • Live integration tests against MLX + DMR; cross-backend smoke tests.

Key concepts introduced

  • Single-model-per-process (MLX) — multiple instances coordinated via the registry.
  • Tool-call shape variance — Ollama returns structured tool_calls; MLX returns text inside content; DMR depends on the GGUF chat template.
  • Apple Metal performance — why these backends had to live host-native from day one.
  • Process-manager-as-Makefile — keeping host-side ops uncomplicated.
After v0.4.0 you can: run any combination of Ollama, MLX, and Docker Model Runner backends on the same Mac Studio, point clients at a single endpoint, and route requests by model id without thinking about which engine is behind which model.

07What's deferred and why

Each item below was actively considered, then deferred to keep v0.1.0–v0.4.0 focused. Most are documented in docs/spec.md §15 (Open follow-ups).

Per-key rate limits / quotas post-v1

v0.2.0's auth makes individual keys identifiable, but doesn't throttle them. For a small home setup with trusted users, the LAN bottleneck is already the limit. Real rate limiting would need a token bucket per key + a metering store.

Usage metering / Prometheus metrics post-v1

Tokens used, requests by model, latency percentiles. structlog logs are enough for ad-hoc analysis; a real metrics endpoint waits for someone to ask for it.

MLX tool-call normalization post-v1

MLX returns tool calls as text inside the message content (the model's chat template controls formatting); Ollama and DMR return structured tool_calls arrays. Normalizing across backends is a per-model parsing exercise that's better done after v0.4.0 so you have real outputs to test against.

Cross-backend embedding fallback post-v1

Currently the registry binds an embedding to one specific model id. A fallback would let the gateway try a list and silently route to whichever is up. Useful operationally but adds non-trivial behavior the user can't see.

Public internet exposure / Let's Encrypt non-goal

The whole point is LAN-only. Caddy in v0.3.0 uses tls internal deliberately. If you need public exposure, that's a different project (and probably needs proper auth + rate limiting + WAF rules first).

Tailscale option maybe-future

An alternative to Caddy + LAN binding: drop both, bind to the Tailscale interface, get end-to-end encryption + cross-network access for free. Considered post-v1 for travelers / multi-location users.

Web UI / multi-tenant admin non-goal

The CLI scripts (mint key, revoke key) cover the small-team case. A web admin panel would change the security model substantially (browser-based auth, sessions, CSRF) and isn't worth the surface for a self-hosted LAN tool.

08Glossary

Terms a newcomer might want a quick definition for.

OpenAI v1 API
The HTTP shape OpenAI publishes — endpoints like /v1/chat/completions with a documented JSON request/ response format. Most third-party LLM tools speak this shape now, which is why this project targets it.
SSE (Server-Sent Events)
A streaming protocol over HTTP. The server sends data: {json}\n\n chunks; the client reads them as they arrive. OpenAI uses SSE for streaming chat completions, terminated by a literal data: [DONE]\n\n.
FastAPI
The Python web framework the gateway uses. Built on top of Starlette (the actual ASGI server) and pydantic (schema validation). Good fit for OpenAI-shaped APIs because pydantic models map 1:1 to the JSON wire format.
Ollama
A popular LLM runner that exposes models locally. Has a built-in OpenAI-compatible HTTP surface at :11434/v1/.... The only fully-wired backend in v0.1.0.
MLX
Apple's array library for machine learning, optimized for Apple Silicon (Metal-backed). mlx_lm.server is a tiny HTTP server around a single MLX-loaded model. Runs only on macOS — no Linux wheels exist.
Docker Model Runner
A Docker Desktop feature (still experimental at the time of writing) that runs LLMs as part of the Docker engine itself. Reachable from containers via model-runner.docker.internal.
Apple Metal
Apple's GPU API. Critical for fast inference on Mac. Not accessible from Docker Desktop on macOS — which is why the model backends in this project run host-native, not containerized.
Argon2id
The modern winner of the password-hashing competition. Memory-hard, slow on purpose, resistant to GPU/ASIC attacks. Used in v0.2.0 for API keys. Verification takes ~50ms — fine for a per-request auth gate.
Caddy
A small web server / reverse proxy. The project uses it for TLS termination via Caddy's built-in local CA (tls internal), which spares you from buying a domain or running Let's Encrypt for a LAN-only service.
structlog
A Python structured-logging library. Output is JSON-per-line, with per-call key/value fields. Replaces stdlib logging in v0.2.0 so logs can be parsed by tools like jq, Grafana, etc.
watchfiles
A Rust-backed Python file-watcher. v0.2.0 uses it to detect changes to config/models.yaml and reload the registry without restarting the process.
host.docker.internal
A special hostname Docker Desktop resolves to the host machine from inside a container. The gateway (in v0.3.0+, containerized) uses it to reach host-native Ollama on :11434.
Capability gate / Tools gate
Two pre-dispatch checks in the chat router: capability gate verifies the requested model declares the relevant capability (e.g. chat or embeddings); tools gate verifies that if the request includes tools, the model declares tools capability. Both fire before any backend call, so invalid requests don't waste compute.
OpenAI error envelope
The JSON shape OpenAI's API returns for errors: {"error": {"type", "message", "param", "code"}}. The gateway uses this shape for every failure path so SDK clients can parse errors uniformly regardless of backend.
BackendAdapter ABC
The abstract base class every backend implementation extends. Defines four async methods (chat_completions, embeddings, health, close). The "routing seam" — the rest of the gateway depends on this interface, never on concrete backend types.
/readyz vs /healthz
/healthz is "is the process alive" (always 200 if anyone answers). /readyz is "is the process ready to serve traffic" — checks dependencies. v0.1.0 only has /healthz; v0.2.0 adds /readyz with per-backend status.
